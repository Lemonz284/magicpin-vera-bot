# 26. Should you use an LLM?

You **can**, but don't make the entire architecture:

```text
JSON → LLM → everything
```

A better architecture would be:

```text
               INPUT CONTEXT
                    ↓
            Context validation
                    ↓
            Signal extraction
                    ↓
           Decision/rule engine
                    ↓
          Select ONE best action
                    ↓
             Message composer
                    ↓
          Structured JSON output
```

The LLM can help with wording, classification, or nuanced category behavior, but your **decision logic should remain controlled**.

This is particularly useful because their scoring emphasizes **decision quality**, not fancy prose.

# First: what is an endpoint?

An endpoint is simply a URL in your backend.

For example:

```text
https://yourbot.com/v1/health
```

When the evaluator sends:

```http
GET /v1/health
```

your server has code that says:

```text
"Oh, they are asking whether I'm alive."
```

and returns a response.

---

# 1. `GET /v1/health`

### What is it for?

To check:

> **"Is your server running?"**

Imagine the evaluator wants to test your bot.

Before doing anything, it can call:

```http
GET /v1/health
```

Your server responds something like:

```json
{
  "status": "ok"
}
```

So the flow is:

```text
Judge
  |
  | GET /v1/health
  ↓
Your server
  |
  | "I'm running"
  ↓
Judge
```

### Why do they need this?

Because your bot is hosted somewhere on the internet.

They need an easy way to check:

```text
Is the server alive?
Can I reach it?
```

This endpoint has **nothing to do with generating messages**.

It's basically a heartbeat.

---

# 2. `GET /v1/metadata`

This is basically:

> **"Tell me information about your bot."**

The evaluator can call:

```http
GET /v1/metadata
```

and your server returns whatever the challenge contract requires.

For example, conceptually:

```json
{
  "name": "My Vera Engine",
  "version": "1.0.0"
}
```

The **exact JSON** should come from the starter package.

### Why?

The evaluator may need information about:

- your bot
- version
- supported API version
- capabilities/configuration

Again, this is **not where the actual message generation happens**.

# 3. `POST /v1/context`

### THIS is one of the important ones.

This means:

The screenshot gives an example like:

with:

```json
  "context_id": "m_001_acme",

  }
```

So their evaluator is basically saying:


Your server receives it and **stores it**.

For example:

```text
Version: 3

Dental Check-up ₹2999
```

You might store that in:

## Why do you need `/context`?

Because the evaluator does **not want to send all merchant information every single time**.

Instead:

```text
/v1/context
     ↓
Store merchant information
     ↓
Later...
/v1/tick
/v1/reply
     ↓
Use the stored information
```

That's what makes your bot **stateful**.

---

# 4. `POST /v1/tick`

This one is easier to understand if you think of a **simulation**.

`tick` basically means:

> **"Time/event has moved forward. Here's the next point in the simulation."**

The evaluator can use it to test whether your bot reacts to changing situations.

Imagine initially:

```text
Searches = 190
Offer = ₹2999
```

Your bot has that stored.

Then the simulator moves forward.

```text
TICK
```

Now maybe new information becomes relevant.

For example:

```text
Searches increased
Offer changed
Festival is approaching
Sales dropped
```

Your bot needs to process the current state and decide what should happen next.

---

### Why do they need `/tick`?

Because they don't want to test your bot with only **one static situation**.

They want to test:

```text
Time 1
 ↓
Your bot makes decision

Time 2
 ↓
New information
 ↓
Your bot adapts

Time 3
 ↓
Another event
 ↓
Your bot adapts again
```

That is what the screenshot means when it talks about:

> "Judges inject fresh facts after submission to test adaptability and grounding."

---

# 5. `POST /v1/reply`

This one is for **conversation**.

Suppose your bot says:

> "190 people nearby are searching for Dental Check Up. Should I promote your ₹2999 offer?"

Now the merchant responds:

> "Yes."

Or:

> "No."

Or:

> "Can you make the offer cheaper?"

The evaluator sends that conversational response to:

```http
POST /v1/reply
```

Your bot then needs to understand the new state of the conversation.

---

## Example

Initially:

```text
Merchant context
     ↓
Your bot

"190 people nearby are searching for
Dental Check Up. Should I promote

```

Then:

```text
Merchant:
"Yes, do it."
```

The evaluator sends that to:

```text
POST /v1/reply
```

Your system can then respond appropriately.

# So why BOTH `/tick` and `/reply`?

Because they test **different things**.

### `/tick`

Represents:

> **Something changed in the environment / simulation.**

```text
New event
New metric
New trigger
New context
```

### `/reply`

Represents:

> **Someone responded to your message.**

```text
Yes
No
Question
Objection
Request
```

So:

```text
TICK  = world/context changed

REPLY = person responded
```

That's the basic idea.

# What each endpoint means in one line

| Endpoint | Meaning |
|---|---|
| `GET /v1/health` | **Are you alive?** |
| `GET /v1/metadata` | **Tell me about your bot.** |
| `POST /v1/context` | **Here is merchant/customer context; remember it.** |
| `POST /v1/tick` | **The simulation/environment moved forward; react to the current state.** |
| `POST /v1/reply` | **The merchant/customer replied; continue the conversation.** |

The **exact request JSON and exact response JSON** for these endpoints are defined by the challenge package. That's the part you should implement exactly rather than inventing your own format.
